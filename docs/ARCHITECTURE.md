# 系统架构与设计决策

本文档说明项目的架构组成，以及几个关键设计选择背后的原因。

## 1. 问题定义

商家在入驻专业号时需要上传营业执照等资质证件。存在一批商家通过复用同一份数字底版（换公司名、换公章、换法人）批量注册账号。

这类问题的难点在于：

- **单张难判**：只看一张证件很难判断真假，但同一份模板出现在多个账号上则高度可疑。
- **全量难审**：每周新入驻账号量级大，全量人工审核不可持续。
- **处置难关联**：按单账号处置无法覆盖背后的批量团伙。

因此把问题从"识别单张证件真假"转换为"发现同版模板的复用群体"，并配套人工复核环节，让识别结果不直接作为处置依据。

## 2. 整体架构

系统分为五个部分：

| 部分 | 职责 | 技术栈 |
| --- | --- | --- |
| 算法管线 | 取数、聚簇、抽样扫簇、数据推送 | Python（FAISS / OpenCV / numpy / pandas） |
| 聚类跑批服务 | 聚簇任务的领取、执行与产物回传 | FastAPI + PostgreSQL |
| 标注平台 | 按簇人工复核打标、结果导出 | FastAPI + PostgreSQL + React 18 |
| 评估看板 | 周度任务管理、浓度计算、多维归因 | FastAPI + ECharts 5 |
| 高危模板入库 | 实锤簇代表图 VLM 判定 + 去重 + 入库 | FastAPI + 视觉大模型 |

各部分通过约定好的数据格式衔接：管线产出"待标注池"，标注平台回收"标注结果"，看板汇总计算"违规浓度"，高危模板入库把复核实锤的簇沉淀为可复用的拦截素材。

## 3. 识别算法

聚簇流程分三步：

1. **候选边生成**：FAISS 对每张图找余弦最近的 top-k 邻居，生成候选边集合。
2. **像素比对建边**：对候选边拉取图片做像素级一致率比对，达到阈值建边。
3. **连通成簇**：Union-Find 把"两两相似"关系归并成分组。

历史上出现过"同一模板被拆成多个子簇"的问题，根因是 top-k 邻居饱和——同一模板图片变多后，每张图的邻居名额被更相似的其他变体占满，真正同模板的图进不了候选集。修复分两步：

- top-k 从 5 扩大到 20；
- 增加簇间补边：簇代表向量做余弦粗筛后，再在候选簇对里找最相似的成员对做像素比对，超阈值即合并。

## 4. 抽样与浓度口径

每周抽三组样本（全行业 / 金融 / 房地产），各自独立计算浓度。

### 抽样量

抽样量由大 N 和上周违规浓度 P 决定：

$$n_0 = \frac{Z^2 \cdot p(1-p)}{e^2}, \qquad n = \frac{n_0 \cdot N}{n_0 + N - 1}$$

- N：上一周该样本组新入驻账户数；
- P：上周该样本组违规浓度（首周用兜底值）；
- e：允许误差，P < 10% 取 2%，P ≥ 10% 取 5%；
- 置信度 99%（z = 2.576）；
- 后半段是有限总体修正，样本量较大时接近 n₀。

抽样用可复现哈希：对 `user_id` 拼盐值求 crc32，按哈希值排序取前 n 个。同一盐值每次抽样结果一致，保证可复盘。

### 扫簇扩展与浓度计算

抽到的账号若命中有效簇（cluster_id ≥ 0），则把同簇其他账号一并带出，供标注员基于完整簇判断。扩展结果用 `is_sample_user` 区分两类账号：

- `is_sample_user = True`：原始抽样账号，进入浓度计算的分子和分母；
- `is_sample_user = False`：同簇扩展账号，只用于辅助判断，不进入分子也不进入分母。

违规浓度 = 该样本组抽样账号中违规账号数 / 该样本组抽样账号总数。

## 5. 标签体系与合规性

标签分两级。一级标签是结论，二级标签是具体类型：

- 实锤造假：有直接物证、可排除合理解释（公章位置完全一致、二维码相同、图片经 P 图处理等）；
- 疑似造假：证据指向造假但存在合理解释空间（电子章批量开具、拍摄背景相似但不完全相同等）；
- 资质挂靠：多家公司使用同一套资质入驻；
- 不违规：合规证书电子版等，因模板相同可能被归入同簇。

识别结果是"疑似模板复用"信号而非处置结论，必须经过人工复核打标后才用于下游统计与处置。这既控制误伤风险，也让浓度评估建立在可审计的人工结论上。

## 6. 双通道标注

标注平台区分两条通道：

- **评估通道**：用于周度浓度评估，按数据集分配标注；
- **审核通道**：用于常态审核，采用抢单制——审核人员自主认领簇，标完即锁定。

两个通道共用同一套标签体系，但评估通道侧重"测水位"，审核通道侧重"个案处置"。

## 7. 质量护栏

数据从取数到看板要经过多道校验，例如：

- 标注池行数与实际上传数是否一致；
- 二级类目加总是否等于一级类目；
- 同一抽样盐值是否可复现；
- 分子分母是否来自同一份标注结果。

同时，针对历史上真实发生过的扩簇错误固化了回归用例（如漏带同簇账户、多带无关簇、set 迭代顺序导致输出不确定等），每次改动扩簇逻辑都必须跑通。

## 8. 高危模板入库

复核为实锤的簇，其代表图会进入高危模板库，供入驻拦截策略复用。链路如下：

1. **挑代表图**：取离簇质心 embedding 最近的一张图作为簇代表（仅聚簇入口）。
2. **VLM 剔纯电子版**：用视觉大模型识别纯 PDF / 白底截图 / 无拍摄痕迹的电子版，只剔除 100% 确定的纯电子版（宁可保留不误剔，unknown 默认保留）。
3. **跨周期去重**：与历史模板库比对，同底版跳过，避免重复入库。
4. **转存 + 入库**：图片转存内部对象存储后写入模板库，支持失败回滚。
5. **人工复核**：VLM 判定结果在前端网格展示，人工勾选保留/剔除后，后端同进程调用机器人完成入库。

设计口径：代表图是电子版则整簇跳过（电子版本身无模板复用价值）；VLM 严格度设为"只剔纯电子版"，控制误剔。

## 9. 漏拦截归因与闭环迭代

浓度评估看清水位、高危模板入库沉淀拦截素材之后，还差最后一环：每个标注为实锤造假的账号，当初机审为什么放行了。

每周通过 `scripts/weekly_hammer_audit_compare.py` 对实锤账号做「实锤图 vs 机审送审图」对照定位（每周三 18:00 自动执行）：

- 筛实锤账号 → 过滤号店（SELLER_PASS，号店属交易部业务）→ 逐 uid 取 `proAccountQualificationSimResList` 相似检索因子与处置结果；
- 比对实锤图与送审图（query_img_url）交集，分三类：
  - **实锤图 = 送审图**：机审见过且命中但放行 → 大模型工作流问题；
  - **实锤图 ≠ 送审图**：账号过审但关键图没进机审 → qcode 拆分 / 换图类；
  - **因子无值**：相似检索没召回 → 算法向量检索问题；
- 根因反馈到对应动作：工作流问题 → 修放行链路；图未进机审 → 修 qcode 拆分；向量检索问题 → 迭代聚簇（top-k、相似阈值、簇间补边）。

这一步把单向的"评估-拦截"升级为"发现 → 拦截 → 漏网归因 → 迭代"的周度闭环。

## 10. 后续方向

- 处置维度从单账号升级到主体级（企业/法人）；
- 建立例行回扫链路与团伙关联扩散能力。
